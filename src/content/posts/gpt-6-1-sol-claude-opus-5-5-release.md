Claude Opus 5.5가 발표된 지 일주일 뒤, OpenAI는 GPT-6.1 Sol을 공개했다. 두 발표에서 눈에 띄는 것은 성능 향상만이 아니다. OpenAI는 상위 모델에 가까운 성능을 더 낮은 단가에 제공한다고 설명했고, Anthropic은 이전 Opus보다 적은 비용으로 작업을 끝낼 수 있다고 강조했다.

코딩 에이전트를 사용할 때 궁금한 것도 결국 비슷하다. **어떤 모델이 더 높은 점수를 받았는가보다, 내가 맡긴 작업을 얼마나 정확하게, 얼마에 끝내는가**가 중요하다.

이 글은 2026년 10월 6일 기준 공식 발표와 API 문서를 바탕으로 한 출시 분석이다. 두 모델을 같은 저장소에서 직접 비교한 사용 후기는 아니다. 회사가 발표한 성능 수치와 비용 절감 주장은 그 출처와 조건을 구분해 읽는다.

## 무엇이 출시됐나

Anthropic은 2026년 9월 22일 [Claude Opus 5.5](https://www.anthropic.com/claude-opus-5-5)를 발표했다. Claude 5.5 제품군의 첫 모델로, 긴 코딩 작업과 지식 업무에서 성능과 효율을 개선했다는 설명이다.

OpenAI의 [GPT-6.1 Sol](https://openai.com/index/introducing-gpt-6-1-sol/)은 GPT-6 Sol의 업데이트다. [TechCrunch의 출시 보도](https://techcrunch.com/2026/09/29/openai-launches-gpt-6-1-sol-says-it-nearly-matches-gpt-6-astra-and-costs-less/)에 따르면 2026년 9월 29일 DevDay에서 공개됐다. OpenAI는 에이전트 코딩, 컴퓨터 사용, 전문 업무에서 GPT-6 Astra에 가까운 성능을 제공한다고 소개한다.

이 블로그에서 앞서 다룬 [GPT-6 Sol·Luna 출시](/posts/gpt-6-sol-luna-claude-opus-5-5-release/)와는 구분할 필요가 있다. 이번 글의 비교 대상은 기존 GPT-6 Sol이 아니라 **GPT-6.1 Sol**이다.

## API 가격부터 비교하기

| 항목 | GPT-6.1 Sol | Claude Opus 5.5 |
| --- | --- | --- |
| 입력 토큰 | $2 | $4 |
| 출력 토큰 | $10 | $20 |
| 캐시 읽기 | $0.10 | $0.20 |
| 캐시 쓰기 | $2.50 | $5 |

가격은 **100만 토큰당 미국 달러, 표준 처리 기준**이다. GPT-6.1 Sol은 [공식 API 모델 문서](https://developers.openai.com/api/docs/models/gpt-6.1-sol), Opus 5.5는 [Anthropic 출시 발표의 가격표](https://www.anthropic.com/claude-opus-5-5)를 참고했다. 구독 요금이나 코딩 도구의 사용량 제한과는 별개의 가격이다.

기본 단가만 보면 GPT-6.1 Sol이 Opus 5.5의 절반이다. 그렇다고 **같은 코딩 작업의 최종 비용도 절반**이라고 결론 내릴 수는 없다. 두 모델이 작업을 끝내기까지 사용하는 토큰과 재시도 횟수가 같다는 보장이 없기 때문이다.

처리 방식에 따른 요율도 확인해야 한다. GPT-6.1 Sol은 입력이 27만 2천 토큰을 초과하면 해당 요청 전체의 입력·캐시 요율이 2배, 출력 요율이 1.5배가 된다. Fast 모드, Batch·Flex 처리, 지역별 처리에도 별도 요율이 있다. Opus 5.5 역시 Fast 모드에서는 입력 $8, 출력 $40으로 표준 단가와 다르다.

## GPT-6.1 Sol: 상위 모델에 가까운 성능을 낮은 단가로

OpenAI 발표의 핵심은 GPT-6.1 Sol이 **Astra에 가까운 성능을 Astra의 표준 입출력 토큰 가격의 5분의 1에 제공한다**는 것이다. 이 비교 대상은 Claude Opus 5.5가 아니라 OpenAI의 GPT-6 Astra다.

공식 API 문서에서 개발자가 확인할 사양은 다음과 같다.

- 컨텍스트 윈도: 105만 토큰
- 최대 출력: 12만 8천 토큰
- 입력: 텍스트와 이미지, 출력: 텍스트
- 추론 강도: `low`, `medium`, `high`, `xhigh`, `max`
- 기본 추론 강도: `medium`

큰 컨텍스트는 많은 자료를 함께 제공할 수 있다는 뜻이지, 저장소 전체를 넣기만 하면 정확하게 이해한다는 보장은 아니다. 긴 입력 할증도 있으므로 필요한 파일을 좁히고 반복되는 문맥을 캐시하는 설계가 여전히 중요하다.

API 연동에서는 **도구 호출에 Responses API를 사용해야 한다**는 점을 확인해야 한다. Chat Completions도 지원하지만 도구 호출 없이 사용하는 경우에 해당한다. 기존 코딩 에이전트가 Chat Completions 기반이라면 모델 이름만 바꿔도 동작할 것이라고 가정하면 안 된다.

출시 설명과 가격을 보면, 복잡한 코딩 작업에 사용할 모델을 검토할 때 GPT-6.1 Sol을 비교 후보에 넣을 근거는 충분하다. 다만 'Astra에 가깝다'는 제품 설명이 내 프로젝트에서도 같은 품질을 보장하지는 않는다.

## Claude Opus 5.5: 토큰 단가뿐 아니라 작업량도 줄이기

Anthropic은 Opus 5.5가 Opus 5보다 일반적인 작업에서 **약 40% 적은 비용**으로 실행된다고 발표했다. 여기서 구분할 숫자가 있다.

- 입력·출력 토큰 단가는 Opus 5보다 20% 낮다.
- 캐시 읽기 단가는 60% 낮다.
- 약 40%의 작업 비용 감소는 작업당 토큰 사용량까지 반영한 회사 측 평가다.

따라서 'Opus 5.5의 모든 토큰 가격이 40% 인하됐다'고 요약하면 틀린 설명이 된다. 가격표의 변화와 실제 작업에서 측정한 비용 변화는 다르다.

Anthropic은 출력 생성 속도도 Opus 5보다 30% 이상 빨라졌다고 설명한다. 하지만 출력 속도가 30% 개선됐다고 전체 코딩 작업 시간이 같은 비율로 줄어드는 것은 아니다. 파일 탐색, 명령 실행, 테스트, 재시도에 걸리는 시간도 있기 때문이다.

코딩 측면에서는 코드베이스 전체에 걸친 마이그레이션과 감사 작업을 강조한다. 발표에는 대규모 코드 변경을 수행한 초기 사용자 사례와 내부 평가가 포함돼 있다. 이런 사례는 어떤 작업을 목표로 한 모델인지 이해하는 데 도움이 되지만, 일반적인 프로젝트에서 그대로 재현되는 결과로 받아들이기는 어렵다.

안전성도 주요 개선 항목이다. Anthropic은 프롬프트 인젝션 방어와 허용 범위 밖 행동에 대한 평가가 개선됐다고 밝혔다. 그렇더라도 에이전트의 파일·명령 권한을 제한하고, 되돌리기 어려운 작업에 승인을 요구하는 운영 원칙을 대체하지는 않는다.

## 발표 벤치마크만으로 승자를 정하기 어려운 이유

두 발표를 나란히 놓으면 어느 모델이 코딩을 더 잘하는지 바로 판단하고 싶어진다. 하지만 **각 회사가 제시한 비교 대상부터 같지 않다.**

OpenAI의 GPT-6.1 Sol 소개는 Astra 대비 성능과 가격을 강조한다. Anthropic의 Opus 5.5 발표에 실린 주요 벤치마크 표에는 GPT-6 Astra와 GPT-5.6 Sol이 등장한다. 이를 GPT-6.1 Sol과 Opus 5.5의 직접 대결 결과로 읽으면 안 된다.

같은 이름의 벤치마크라도 다음 조건을 확인해야 한다.

- 에이전트 실행 환경과 사용할 수 있는 도구
- 추론 강도와 토큰·시간 예산
- 재시도 허용 여부와 평가 횟수
- 안전장치 개입 시 실패 처리 또는 대체 모델 사용 여부

실제로 Anthropic은 일부 평가에서 안전장치가 개입하면 특정 작업을 다른 Claude 모델로 완료했다고 명시한다. 이런 주석을 빼고 점수만 인용하면 비교 조건을 놓치게 된다.

벤치마크는 후보를 좁히는 자료다. 내가 사용하는 저장소에서의 완료율과 검토 부담까지 대신 측정해 주지는 않는다.

## 개발자라면 무엇을 측정할까

모델을 고를 때는 토큰 단가보다 **검증된 작업 하나를 끝내는 비용**을 보는 편이 실용적이다. 저렴한 모델이 여러 번 실패하면 처음부터 더 비싼 모델을 쓰는 것보다 비용과 시간이 커질 수 있다. 반대로 어려운 모델이 필요하지 않은 작업에 항상 최고 성능 모델을 쓰면 불필요한 지출이 생긴다.

두 모델을 직접 비교한다면 같은 저장소의 같은 커밋에서 아래 과제를 맡겨볼 수 있다.

1. **원인이 명확한 버그 수정**: 재현 조건을 주고 회귀 테스트까지 작성하게 한다.
2. **여러 파일에 걸친 변경**: 기존 동작을 유지하면서 공통 타입이나 API 사용 방식을 수정하게 한다.
3. **원인 조사**: 실패 로그를 제공하고 원인 후보를 좁힌 뒤 최소 수정안을 만들게 한다.

각 실행에서는 허용 도구, 권한, 추론 강도, 제한 시간을 기록한다. 추론 강도 이름이 같아도 모델 간 계산량이 같다고 가정하지 않고, 가능한 한 같은 운영 제약을 적용한다. 한 번의 성공만으로 판단하지 않도록 반복 실행도 필요하다.

| 비교 항목 | 확인할 내용 |
| --- | --- |
| 정확성 | 요구사항 충족, 테스트 통과, 기존 동작 유지 |
| 수정 범위 | 불필요한 변경, 누락된 파일, 새로 생긴 문제 |
| 검토 부담 | 사람이 다시 조사하거나 수정한 양 |
| 시간 | 검증된 완료까지의 시간과 재시도 횟수 |
| 비용 | 입력·출력·캐시와 별도 도구 사용료를 포함한 실제 청구액 |

API 사용료와 사람의 검토 시간은 우선 따로 기록하는 편이 좋다. 검토 시간을 금액으로 환산하려면 별도의 기준이 필요하기 때문이다. 테스트를 통과하지 못한 실행의 비용도 제외하지 않아야 실제 운영 비용에 가까워진다.

## 정리

GPT-6.1 Sol은 상위 모델에 가까운 성능을 낮은 단가에 제공하는 방향을, Claude Opus 5.5는 이전 세대보다 적은 토큰과 비용으로 작업을 완료하는 방향을 강조한다. 두 발표 모두 코딩 에이전트를 평가할 때 비용 효율을 함께 봐야 한다는 점을 보여준다.

현재 확인할 수 있는 것은 제품의 목표, 공개 사양, 가격, 회사 측 평가 결과다. **내 프로젝트에서 어느 모델이 더 효율적인지는 같은 작업을 실행하고 결과를 검증한 뒤에야 말할 수 있다.**

지금은 한 모델을 승자로 정하기보다, 단가와 완료율, 재작업까지 함께 비교할 기준을 준비하는 것이 더 유용하다.
