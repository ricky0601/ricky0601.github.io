개발 블로그의 중심은 글이다. 방문자는 제목을 보고 글을 열고, 내용을 읽고, 관련 글로 이동한다. 글을 읽는 데 로그인이나 실시간 데이터 처리가 필요한 것은 아니다.

DONGGEON.LOG는 Astro와 TypeScript로 만들고 GitHub Pages에 배포한다. 이 글에서는 현재 구현을 기준으로, Astro의 어떤 특성이 글 중심의 블로그에 맞는지 정리한다. 다른 프레임워크보다 무조건 낫다는 비교보다는 이 프로젝트에 필요한 것과 구현 방식의 관계에 초점을 맞춘다.

## Astro란 무엇인가

[Astro](https://astro.build/)는 블로그, 문서, 소개 페이지처럼 콘텐츠를 전달하는 웹사이트에 초점을 맞춘 웹 프레임워크다. 페이지와 재사용 컴포넌트를 작성하고, Markdown 콘텐츠를 읽어 웹페이지로 구성할 수 있다.

기본 컴포넌트 파일은 `.astro` 확장자를 사용한다. 파일 안에서 데이터를 준비하는 코드와 HTML 형태의 마크업을 함께 작성할 수 있으며, 컴포넌트는 빌드 단계나 서버에서 HTML로 렌더링된다. 컴포넌트를 사용했다는 이유만으로 그 코드를 모두 브라우저에서 실행하는 것은 아니다.

핵심 개념 중 하나는 **아일랜드 아키텍처(islands architecture)**다. 페이지의 대부분은 정적인 HTML로 제공하고, 상호작용이 필요한 부분만 독립적인 '섬'처럼 활성화하는 방식이다. 예를 들어 글 본문은 HTML로 보여주고, 상태 관리가 필요한 계산기만 브라우저에서 동작하는 컴포넌트로 만들 수 있다.

필요하다면 React나 Vue 등의 UI 프레임워크를 통합하고, `client:load`나 `client:visible` 같은 지시자로 해당 컴포넌트를 언제 활성화할지 지정할 수 있다. 이런 기능을 반드시 사용해야 하는 것은 아니다. 단순한 동작은 일반 JavaScript로 구현할 수도 있다.

또한 Astro가 정적 사이트만 만드는 도구인 것은 아니다. 어댑터와 설정에 따라 요청 시 서버에서 페이지를 렌더링하는 방식도 지원한다. 이 블로그에서는 그중 **빌드할 때 페이지를 미리 만드는 정적 출력 방식**을 사용한다.

## 블로그에 필요한 것부터 정리하기

이 블로그에서 중요한 것은 다음과 같다.

- Markdown 파일로 글을 작성하고 수정할 수 있을 것
- 제목, 설명, 날짜, 태그를 일관된 구조로 관리할 것
- 본문을 읽기 쉬운 HTML로 제공할 것
- 검색 엔진과 구독 도구가 글을 발견할 수 있을 것
- 별도의 애플리케이션 서버 없이 배포할 수 있을 것

반면 현재는 사용자 계정, 데이터베이스, 실시간 알림이 필요하지 않다. 검색과 목차도 당장 추가하기보다 콘텐츠가 쌓인 뒤 필요성을 판단할 항목이다.

이렇게 범위를 놓고 보면, 서버에서 매 요청마다 페이지를 생성하기보다 빌드할 때 HTML을 만드는 정적 사이트 방식이 잘 맞는다.

## 읽을 때마다 만들지 않고, 배포할 때 만들기

현재 Astro 설정은 정적 출력을 명시한다.

```js
export default defineConfig({
  site: 'https://ricky0601.github.io',
  output: 'static',
  // sitemap 등 나머지 설정은 생략
});
```

글을 작성하고 사이트를 빌드하면 배포할 정적 파일이 생성된다. 방문자의 요청을 처리하기 위해 별도의 Astro 애플리케이션 서버를 계속 실행할 필요는 없다.

이는 글이 바뀌는 시점과 글을 읽는 시점을 분리하는 방식이다. 새 글이나 수정 내용을 공개하려면 다시 빌드하고 배포해야 하지만, 요청마다 최신 데이터를 조회하지 않는 블로그에서는 자연스러운 흐름이다.

정적 사이트라고 해서 자동으로 빠른 사이트가 되는 것은 아니다. 이미지 크기, 폰트, CSS, 추가 스크립트도 실제 로딩 경험에 영향을 준다. 여기서의 선택 기준은 측정하지 않은 성능 우위가 아니라, 필요한 페이지를 미리 생성할 수 있다는 구조다.

## 글은 Markdown으로, 규칙은 Content Collections로

게시글은 `src/content/posts` 아래의 Markdown 파일로 관리한다. 제목과 발행일 같은 메타데이터는 frontmatter에 작성한다.

```yaml
---
title: "문제를 해결하며 배운 것"
description: "문제의 재현 조건과 원인을 좁힌 과정을 기록합니다."
publishedAt: 2026-10-01
category: "Troubleshooting"
tags:
  - CSS
draft: true
---
```

Markdown은 본문 작성에 집중하기 좋지만, 메타데이터의 형식까지 스스로 보장하지는 않는다. 파일마다 필드 이름이나 타입이 달라지면 목록과 상세 페이지에서 문제가 생길 수 있다.

이 부분은 Astro Content Collections의 스키마로 관리한다. 현재 `src/content.config.ts`에서는 제목과 설명을 비어 있지 않은 문자열로 정의하고, 발행일은 날짜로 변환하며, 태그는 문자열 배열로 받는다.

글을 파일로 관리하면서도 페이지 코드가 사용하는 데이터에는 공통 규칙을 둘 수 있다. 다만 스키마가 확인하는 것은 데이터의 형식이다. 제목이 적절한지, 설명이 본문과 맞는지, 기술적인 내용이 정확한지는 별도로 검토해야 한다.

## 초안과 공개 글을 구분하기

작성 중인 글도 같은 폴더에서 관리하되 `draft: true`로 표시한다. 공개 글을 조회하는 공통 함수는 초안을 제외한다.

```ts
export async function getPublishedPosts() {
  const posts = await getCollection('posts', ({ data }) => !data.draft);
  return posts.sort((a, b) => b.data.publishedAt.valueOf() - a.data.publishedAt.valueOf());
}
```

이 구조에서는 공개 글 조회 조건을 한곳에 모을 수 있다. 목록이나 피드처럼 공개 콘텐츠를 사용하는 곳에서 각자 다른 기준을 만드는 일을 줄이는 데 도움이 된다.

초안 표시는 비밀 정보를 보호하는 수단은 아니다. 공개 저장소에 커밋한 파일은 사이트에 노출되지 않더라도 저장소에서 읽을 수 있으므로, 민감한 내용은 초안에도 넣지 않아야 한다.

## 정적인 읽기 화면과 필요한 상호작용을 구분하기

Astro는 기본적으로 컴포넌트를 서버나 빌드 단계에서 HTML로 렌더링하고, 필요한 부분에 클라이언트 상호작용을 추가할 수 있다.

글 제목, 본문, 태그 링크를 보여주는 데 반드시 클라이언트 프레임워크가 필요한 것은 아니다. HTML과 CSS로 해결할 수 있는 부분은 그대로 두고, 브라우저에서 동작해야 하는 기능이 생겼을 때 JavaScript의 필요성을 판단할 수 있다.

이것이 JavaScript를 전혀 쓰지 않겠다는 뜻은 아니다. 블로그에서는 화면 전체의 상태 관리부터 도입하기보다, 읽기 경험에 필요한 동작이 무엇인지 먼저 따지는 편이 적절하다.

## GitHub Pages까지 이어지는 배포 구조

현재 배포는 `main` 브랜치에 push하면 GitHub Actions가 사이트를 빌드하고 GitHub Pages에 배포하는 방식이다.

글 수정과 코드 변경이 같은 저장소의 변경 이력으로 남고, 정적 산출물을 배포하므로 별도의 애플리케이션 서버를 운영하지 않는다. Markdown 파일을 수정하는 작업이 사이트 업데이트로 이어진다.

물론 Git 기반 작성 방식에도 제약은 있다. 브라우저에서 글을 작성하는 CMS와 달리 파일 편집과 커밋, 배포 흐름을 알아야 한다. 여러 작성자가 함께 운영하거나 편집 화면이 필요해진다면 지금의 구조를 다시 검토할 수 있다.

## Astro를 쓰는 것과 블로그를 완성하는 것은 다르다

프레임워크를 선택했다고 접근성과 SEO가 자동으로 완성되지는 않는다. 페이지별 제목과 설명, canonical URL, 제목 단계, 키보드 포커스, RSS와 sitemap은 실제 구현에서 챙겨야 한다.

Astro는 이 블로그에서 정적 페이지와 콘텐츠를 구성하는 기반이다. 어떤 정보를 보여줄지, 어떻게 읽기 좋게 배치할지, 글의 품질을 어떻게 유지할지는 여전히 프로젝트의 몫이다.

현재 구조에서 Astro가 잘 맞는 이유는 가장 많은 기능을 제공해서가 아니다. **글을 파일로 관리하고, 규칙에 맞게 읽어 들이고, 정적 페이지로 배포하는 흐름이 블로그의 요구사항과 맞기 때문이다.**

앞으로 기능을 추가할 때도 같은 기준을 적용할 수 있다. 구현할 수 있다는 이유보다, 글을 쓰거나 읽는 데 실제로 필요한지를 먼저 확인하는 것이다.
